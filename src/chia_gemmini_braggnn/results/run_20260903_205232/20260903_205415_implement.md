## Summary

I changed the Gemmini systolic array size from the default **16x16** to **8x8** in two places within the `generators/gemmini` submodule:

### 1. `generators/gemmini/src/main/scala/gemmini/Configs.scala`
In `GemminiConfigs.defaultConfig` (the primary default configuration used by Chipyard's `GemminiRocketConfig`), I changed:
- `meshRows = 16` → `meshRows = 8`
- `meshColumns = 16` → `meshColumns = 8`

I also updated the accompanying doc comment to reflect the new "8x8" default.

### 2. `generators/gemmini/src/main/scala/gemmini/GemminiConfigs.scala`
In the `GemminiArrayConfig` case class default parameters, I changed:
- `meshRows: Int = 16` → `meshRows: Int = 8`
- `meshColumns: Int = 16` → `meshColumns: Int = 8`

### Impact
- The **`GemminiRocketConfig`** (the standard Chipyard Gemmini configuration) uses `GemminiConfigs.defaultConfig`, so it now builds an 8x8 systolic array.
- Other derived configs (`chipConfig`, `leanConfig`, `leanPrintfConfig`, `dummyConfig`) all derive from `defaultConfig` via `.copy()`, so they inherit the 8x8 size too.
- The 8x8 array satisfies Gemmini's square-array requirement (`meshColumns * tileColumns == meshRows * tileRows` with `tileRows = tileColumns = 1`), and the resulting 64-bit wide data path per row still fits within the 128-bit system bus used by the Gemmini config.

I left `DSEConfigs.scala` and `largeChipConfig` untouched, since those are explicitly-configured design-space-exploration/large variants (with deliberate 16x16/32x32 mesh sizes) rather than the default configuration.
