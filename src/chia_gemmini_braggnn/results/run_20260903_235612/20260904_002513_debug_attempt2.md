### Root Cause

The error was `ClassNotFoundException: chipyard.Generator`, which occurred because the classpath jar `/home/ray/chipyard/.classpath_cache/chipyard.jar` was **0 bytes (empty)**.

Here's what happened:

1. Chipyard's build system (`common.mk` → `variables.mk`) builds a fat assembly jar for the `chipyard` SBT project and copies it to the cache path `.classpath_cache/chipyard.jar` via the `run_sbt_assembly` macro:
   ```
   $(SBT) ";project chipyard; set assembly / assemblyOutputPath := file(\".../.classpath_cache/chipyard.jar\"); assembly" && touch .../.classpath_cache/chipyard.jar
   ```

2. During the failing build, SBT reported `Assembly jar up to date: /home/ray/chipyard/generators/chipyard/target/scala-2.13/chipyard-assembly-1.6.jar`. This is the classic sbt-assembly **incremental caching** behavior: sbt-assembly hashes the inputs (via `assembly-cacheKey-2.13.16`) and if it considers the assembly unchanged, it **skips writing the jar entirely** — even when the output path was changed to a new location (`.classpath_cache/chipyard.jar`).

3. Because sbt skipped producing the jar at the new output path, the `&& touch .../.classpath_cache/chipyard.jar` step created an **empty 0-byte file** at the cache location. (Meanwhile the real 427MB jar remained only at the old default SBT target path.)

4. The subsequent `java -cp /home/ray/chipyard/.classpath_cache/chipyard.jar chipyard.Generator ...` command tried to load the empty jar → `ClassNotFoundException: chipyard.Generator`.

### What I Changed / Fixed

The root fix is to ensure `.classpath_cache/chipyard.jar` is properly populated rather than a 0-byte placeholder:

1. Removed the stale sbt-assembly cache under `generators/chipyard/target/streams/_global/assembly/` (specifically `assembly-outputs-2.13.16` and `assembly-cacheKey-2.13.16`) so sbt-assembly no longer considers the output "up to date" against the wrong output path.

2. Verified that the actual fully-built assembly (`chipyard-assembly-1.6.jar`, 427MB, which already contained the latest gemmini source since it was built after the gemmini edits) was used to populate `.classpath_cache/chipyard.jar`.

3. Updated/confirmed the assembly cache stream (`assembly-outputs-2.13.16`) now points at `/home/ray/chipyard/.classpath_cache/chipyard.jar` so future builds write to the correct location.

4. Verified the fix:
   - `chipyard.jar` is now 427MB (not 0 bytes) and contains `chipyard/Generator.class`.
